\begin{abstract}
\noindent
Multi-agent applications are usually built by wiring language-model agents into a graph: the developer declares nodes, declares edges, compiles the result, and repeats the exercise whenever the shape of the workflow changes. We describe \AR{}, the workflow primitive of the open-source Swarms framework, which replaces that construction with one string. Two operators carry the whole language: \code{->} places steps in sequence and a comma runs the agents of a step in parallel, so \code{"Planner -> Tech, Market, Legal -> Writer"} is a complete five-agent workflow. Because a step may itself be a named workflow, the language expresses every series-parallel composition of agents, and changing the topology is a string assignment that is validated on the spot.
We give the grammar and execution semantics of the language, compare the code it takes to express the same workflow in LangGraph, AutoGen, LangChain, Agno and CrewAI, and release a benchmark suite that measures orchestration overhead, memory, construction cost and re-specification cost over four workflow shapes from 8 to 512 agents with a stubbed model. For wide workflows, \AR{} adds 37 to 42\,ms of overhead at 512 agents, 2.5 times less than LangGraph with function nodes and about 9 times less than LangGraph with agent nodes, and it changes topology between 9 and about 100 times faster than rebuilding a LangGraph graph. For chains of hundreds of steps it is slower than frameworks that do constant work per step, because every agent reads a growing shared conversation.
We also report where the design costs something: the language has no conditional edges or cycles, every agent reads the whole shared conversation, and parallel steps hold one thread per agent.
\end{abstract}

\section{Introduction}

A single language-model agent is a loop around a model call, often one that interleaves reasoning with tool use~\cite{react}. A multi-agent system is a set of such loops plus a rule for who runs when and who sees whose output~\cite{survey_guo,survey_wang}. Most of the engineering effort in a multi-agent application goes into the second part, and it is also where such systems tend to break: a study of failures in multi-agent systems attributes a large share of them to how the system is specified and how agents are coordinated, not to the individual agents~\cite{mast}. The dominant way to express it is a graph API: LangGraph~\cite{langgraph} builds a \code{StateGraph} from \code{add\_node} and \code{add\_edge} calls and compiles it; AutoGen~\cite{autogen} offers a \code{DiGraphBuilder} that feeds a \code{GraphFlow} team; CrewAI~\cite{crewai} attaches agents to an ordered list of tasks; Agno~\cite{agno} nests \code{Step} and \code{Parallel} objects inside a \code{Workflow}.

These APIs are general, and generality has a price that is paid on every workflow, including the simple ones. A widely read practitioner guide~\cite{anthropic_agents} describes a small set of recurring patterns, and three of them are purely structural: a chain in which each step refines the last, a fan-out in which several agents work on the same input at once, and a fan-out followed by a step that merges the results. For these shapes a graph API asks the developer to write roughly two calls per agent, to keep node names and edge endpoints consistent by hand, and to rebuild and recompile when an agent is moved.

\AR{} starts from the observation that these shapes are all compositions of two operations, \emph{then} and \emph{together}, and that two operations fit in a string. The name and the notation follow \code{einsum}~\cite{numpy} and einops~\cite{einops}, which showed that a compact string can replace a family of tensor-manipulation calls without losing clarity. In \AR{}, a workflow is written as

\begin{lstlisting}[style=plain]
Planner -> Tech, Market, Legal -> Writer
\end{lstlisting}

\noindent which reads as it runs: the planner first, three specialists together, then the writer. The agents are ordinary objects defined once; the string only arranges them, and rearranging them is editing the string.

This paper makes four contributions.
\begin{enumerate}
  \item A precise description of the \AR{} flow language: its grammar, its validation rules and its execution semantics, including nested workflows (Section~\ref{sec:language}) and the shared-conversation execution model (Section~\ref{sec:execution}).
  \item A side-by-side comparison of the code needed to express the same workflow in six frameworks, with a count of the calls each one requires as a function of workflow size (Section~\ref{sec:code}).
  \item An open benchmark suite, \code{tests/benchmark\_agent\_rearrange.py} in the Swarms repository, that runs the same four workflow shapes through each framework with a stubbed model and reports orchestration overhead, memory, threads, construction time and re-specification time (Section~\ref{sec:eval}).
  \item An account of the limits of the approach, stated as plainly as the results (Section~\ref{sec:limits}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Graph-based orchestration.}
LangGraph~\cite{langgraph} models an application as a state machine. Nodes are functions or agents that read and update a typed state, edges may be conditional, cycles are allowed, and state can be checkpointed. AutoGen~\cite{autogen} began with conversation patterns between agents and later added \code{GraphFlow}, a directed graph of agents with optional edge conditions. Both can express anything \AR{} can and much that it cannot. Their cost is verbosity for simple shapes and a compile step between specification and execution. Semantic Kernel~\cite{semantic_kernel} and Magentic-One~\cite{magentic_one} take a third route, in which an orchestrating agent plans the order of work at run time.

\paragraph{Pipelines and expression languages.}
LangChain's expression language~\cite{langchain} composes runnables with the \code{|} operator and runs dictionaries of runnables in parallel. It is concise, but it composes data transformations and not agents: the developer writes the function that turns the outputs of one parallel step into the input of the next. Agno~\cite{agno} workflows nest \code{Step}, \code{Parallel}, \code{Loop} and \code{Router} objects. CrewAI~\cite{crewai} runs an ordered list of tasks, each bound to an agent, and marks tasks asynchronous to run them side by side. DSPy~\cite{dspy} composes prompt programs as modules and optimises them, an orthogonal concern.

\paragraph{Role-based and conversational systems.}
CAMEL~\cite{camel}, MetaGPT~\cite{metagpt} and ChatDev~\cite{chatdev} fix the organisation of agents in advance, as role-play pairs or as a software company with a standard operating procedure. AgentVerse~\cite{agentverse} and generative agents~\cite{generative_agents} study larger groups whose interaction structure emerges from the simulation. Mixture-of-Agents~\cite{moa} fixes a layered topology in which each layer of agents reads the answers of the layer before. That topology is exactly a flow of parallel steps, and is one line in the language described here.

\paragraph{Parallel sampling and debate.}
Several results show that running the same question through many model calls and combining the answers improves accuracy: self-consistency votes over sampled reasoning paths~\cite{self_consistency}, multi-agent debate lets agents revise in rounds after reading one another~\cite{debate}, and simple sampling-and-voting keeps improving as agents are added~\cite{more_agents}. Tree of Thoughts~\cite{tot} searches over branches of partial solutions. Structurally these are fan-outs, or fan-outs repeated in layers, which is the shape the comma operator states.

\paragraph{Topology as an object of optimisation.}
A recent line of work treats the arrangement of agents as something to search over and not to hand-write. GPTSwarm~\cite{gptswarm} represents a system as a computational graph and optimises its edges; DyLAN~\cite{dylan} selects agents and their connections per task; MacNet~\cite{macnet} studies directed acyclic topologies of up to a thousand agents; ADAS~\cite{adas} and AFlow~\cite{aflow} search the space of agentic systems and workflows directly, and LLMCompiler~\cite{llmcompiler} plans a dependency graph of calls so that independent ones run in parallel. This work needs a representation of topology that is compact, easy to generate and cheap to validate and to swap. A flow string is one such representation, and Section~\ref{sec:eval} measures the cost of swapping it.

\paragraph{Agent SDKs without a workflow layer.}
The OpenAI Agents SDK~\cite{openai_agents}, which grew out of the experimental Swarm library~\cite{openai_swarm}, and Pydantic AI~\cite{pydantic_ai} provide agents, tools and handoffs, and leave composition to ordinary Python: \code{asyncio.gather} for parallel work, sequential awaits for chains. LlamaIndex~\cite{llamaindex} offers event-driven workflows and a handoff-based \code{AgentWorkflow}.

\paragraph{Workflow theory.}
The two operators of \AR{} are the series and parallel compositions of series-parallel graphs~\cite{sp_graphs}, and correspond to the \emph{sequence}, \emph{parallel split} and \emph{synchronisation} patterns in the workflow-pattern catalogue of van der Aalst et al.~\cite{workflow_patterns}. The catalogue's choice and iteration patterns are the ones \AR{} leaves out. The pairing of a parallel step with a step that merges its results is the fan-out and fan-in of data-parallel systems such as MapReduce~\cite{mapreduce}, a chain is a pipeline in the sense of Kahn's process networks~\cite{kahn}, and general-purpose workflow engines such as Airflow~\cite{airflow} express the same structures as explicit task graphs.

\paragraph{Swarms.}
Swarms~\cite{swarms} is an open-source Python framework for multi-agent systems. Its building block is the \code{Agent} class; structures such as \code{SequentialWorkflow}, \code{ConcurrentWorkflow}, \code{GraphWorkflow}, \code{MixtureOfAgents} and \code{HierarchicalSwarm} each fix one orchestration pattern. \AR{} is the structure that lets the user write the pattern down.

\section{The Flow Language}
\label{sec:language}

\subsection{Grammar}

A flow is a non-empty sequence of steps separated by \code{->}. A step is a non-empty, comma-separated list of names. A name refers to a member registered with the workflow: an agent, by its \code{agent\_name}, or another workflow, by its \code{name}. Whitespace around names is ignored.

\begin{lstlisting}[style=plain]
flow  ::=  step ( "->" step )*
step  ::=  name ( "," name )*
name  ::=  the name of a registered agent or nested workflow
\end{lstlisting}

\noindent A flow with $N$ names in $L$ steps is therefore a string with $N$ names, $L-1$ arrows and $N-L$ commas. Three special cases are worth naming: a flow with no commas is a chain, a flow with no arrows is a pure fan-out, and a flow whose steps all have several names is the layered topology of Mixture-of-Agents~\cite{moa}.

\subsection{Semantics}

Steps run in order. A step with one name runs that member. A step with several names runs all of them at once and completes when the last one finishes. Every member reads the conversation so far and appends its answer to it, so a member in step $k$ sees the task and every answer from steps $1$ to $k-1$. Members of the same step do not see one another's answers, and their answers are recorded in the order they are written in the flow, not the order they finish, so the transcript is deterministic. Setting \code{max\_loops} to $m$ runs the whole flow $m$ times over the growing conversation.

In graph terms, consecutive steps are joined by a complete bipartite set of edges: every member of step $k+1$ depends on every member of step $k$. Table~\ref{tab:flows} lists common shapes.

\begin{table}[ht]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
Shape & Flow & Parsed steps \\
\midrule
Chain & \code{a -> b -> c} & \code{[[a], [b], [c]]} \\
Fan-out & \code{a, b, c} & \code{[[a, b, c]]} \\
Fan-out, fan-in & \code{a -> b, c -> d} & \code{[[a], [b, c], [d]]} \\
Layered & \code{a, b -> c, d -> e} & \code{[[a, b], [c, d], [e]]} \\
Revisit & \code{writer -> critic -> writer} & \code{[[writer], [critic], [writer]]} \\
\bottomrule
\end{tabular}
\caption{Flows and the steps they parse to. A name may appear more than once; each occurrence is a separate invocation of the same agent.}
\label{tab:flows}
\end{table}

\subsection{Validation and inspection}

A flow is checked when the workflow is constructed, when the flow is replaced and before each run. The check rejects an empty flow, an empty step such as the one in \code{"a -> -> b"}, and any name that is not registered, with a \code{ValueError} that names the offending step or agent. No model call is made before the flow is known to be well formed.

The \code{explain} method prints the resolved plan without running anything, which makes a flow testable in continuous integration:

\begin{lstlisting}[style=plain]
>>> workflow.explain()
Flow: Planner -> Tech, Market, Legal -> Writer

Step 1: Planner              [sequential]
Step 2: Tech, Market, Legal  [parallel, 3 agents]
Step 3: Writer               [sequential]

3 steps, 5 agent invocations across 1 loop(s).
\end{lstlisting}

\subsection{Nesting and expressiveness}

Any object with a \code{name} and a \code{run} method can be registered as a member, including another \AR{}. A nested workflow is a single name in the outer flow and runs as one step. This closes the language under composition: a parallel branch can be a chain, a step of a chain can be a fan-out, to any depth.

\begin{lstlisting}
experts = AgentRearrange(
    name="Experts",
    agents=[tech, market, legal],
    flow="Tech -> Market, Legal",
)
workflow = AgentRearrange(
    agents=[planner, experts, writer],
    flow="Planner -> Experts -> Writer",
)
\end{lstlisting}

The class of orders expressible this way is the class of series-parallel orders~\cite{sp_graphs}: those built from single agents by repeatedly placing two workflows in sequence or side by side. The smallest dependency structure outside the class is the ``N'' shape, in which $c$ depends on $a$ and $b$ while $d$ depends on $b$ alone. \AR{} cannot express it exactly; it can only over-approximate it by letting $d$ also wait for $a$. Section~\ref{sec:limits} returns to this.

\section{Execution Model}
\label{sec:execution}

\paragraph{One shared conversation.}
An \AR{} holds a single conversation. A run resets it, records the task, and then executes the steps. Before a member runs, the conversation is rendered for that member as chat messages in which the member's own earlier answers carry the \code{assistant} role and everything else is attributed input; the newest turn becomes the member's task. After the member returns, only its answer, not its private scratch work, is appended. The developer never writes the code that moves outputs from one agent to the next, which is the code that pipeline languages leave to the user.

\paragraph{Position awareness.}
A member of a sequential step is told which members come immediately before and after it in the flow, as a system message that is not written to the shared conversation. With \code{team\_awareness=True} the full step structure is added to the conversation once, at the start of the run.

\paragraph{Parallel steps.}
The members of a parallel step run on a thread pool sized to the step. Each receives its own rendering of the conversation as it stood when the step began. Results are written back in flow order once all have finished. An exception in any member propagates to the caller.

\paragraph{Outputs.}
The \code{output\_type} parameter selects what \code{run} returns from the conversation: the full transcript as a string or list, a dictionary, or only the final answer.

\paragraph{Rearranging.}
\code{set\_custom\_flow} replaces the flow. The new string is validated first, and on failure the old flow is kept and the error is raised at the call site:

\begin{lstlisting}
workflow.set_custom_flow("Planner -> Tech -> Market -> Legal -> Writer")

workflow.set_custom_flow("Planner -> Tehc -> Writer")
# ValueError: Agent 'Tehc' is not registered.
# workflow.flow is unchanged
\end{lstlisting}

\noindent Agents are not rebuilt and nothing is compiled; the parsed steps are cached against the flow string and refreshed when it changes. Members can also be added and removed with \code{add\_agent} and \code{remove\_agent}.

\paragraph{Entry points.}
Besides \code{run}, the class offers \code{batch\_run} and \code{concurrent\_run} for many tasks, each on an independent copy of the workflow so transcripts never mix, \code{run\_async} for use inside an event loop, and \code{run\_stream} and \code{arun\_stream} for token streaming, where tokens from the members of a parallel step are interleaved and labelled by agent. The same flow string is accepted by \code{SwarmRouter} with \code{swarm\_type="AgentRearrange"}.

\section{Code Comparison}
\label{sec:code}

We write one workflow in three frameworks: a planner, three specialists that work in parallel, and a writer that reads all three. Agent construction is similar everywhere and is shown only for \AR{}; the comparison is about the code that states the topology.

\listinghead{AgentRearrange}
\begin{lstlisting}
from swarms import Agent, AgentRearrange

planner = Agent(agent_name="Planner", model_name="gpt-5.4", max_loops=1)
tech    = Agent(agent_name="Tech",    model_name="gpt-5.4", max_loops=1)
market  = Agent(agent_name="Market",  model_name="gpt-5.4", max_loops=1)
legal   = Agent(agent_name="Legal",   model_name="gpt-5.4", max_loops=1)
writer  = Agent(agent_name="Writer",  model_name="gpt-5.4", max_loops=1)

workflow = AgentRearrange(
    agents=[planner, tech, market, legal, writer],
    flow="Planner -> Tech, Market, Legal -> Writer",
)
report = workflow.run("Assess launching a payments product in the EU.")
\end{lstlisting}

\listinghead{LangGraph}
\begin{lstlisting}
from langgraph.graph import END, START, MessagesState, StateGraph

graph = StateGraph(MessagesState)
graph.add_node("Planner", planner)
graph.add_node("Tech", tech)
graph.add_node("Market", market)
graph.add_node("Legal", legal)
graph.add_node("Writer", writer)
graph.add_edge(START, "Planner")
graph.add_edge("Planner", "Tech")
graph.add_edge("Planner", "Market")
graph.add_edge("Planner", "Legal")
graph.add_edge(["Tech", "Market", "Legal"], "Writer")
graph.add_edge("Writer", END)
app = graph.compile()
report = app.invoke(
    {"messages": [("user", "Assess launching a payments product in the EU.")]}
)
\end{lstlisting}

\listinghead{AutoGen GraphFlow}
\begin{lstlisting}
from autogen_agentchat.teams import DiGraphBuilder, GraphFlow

builder = DiGraphBuilder()
for agent in (planner, tech, market, legal, writer):
    builder.add_node(agent)
for expert in (tech, market, legal):
    builder.add_edge(planner, expert)
    builder.add_edge(expert, writer)
team = GraphFlow(
    participants=builder.get_participants(), graph=builder.build()
)
report = await team.run(task="Assess launching a payments product in the EU.")
\end{lstlisting}

Table~\ref{tab:spec} generalises the count. For a flow of $N$ agents in $L$ steps of widths $w_1,\dots,w_L$, \AR{} needs one string whatever the size. LangGraph needs about two calls per agent. AutoGen needs one edge per pair of agents in consecutive steps, which is quadratic in the step width. The nested-object styles of Agno and LangChain and the task list of CrewAI sit in between.

\begin{table}[ht]
\centering
\small
\begin{tabularx}{\linewidth}{@{}lXr@{}}
\toprule
Framework & Topology specification for $N$ agents in $L$ steps & 5-agent example \\
\midrule
\AR{} & one string with $N$ names & 1 \\
LangGraph \code{StateGraph} & constructor, $N$ \code{add\_node}, about $N$ \code{add\_edge}, \code{compile} & 13 \\

\bottomrule
\end{tabularx}

\label{tab:spec}
\end{table}

The count understates one difference. In the graph APIs the topology is spread across statements that must agree with one another: a node name used in an edge must match a node added earlier, and moving an agent means finding and editing every edge that touches it. In \AR{} the topology is one value. It can be stored in a configuration file, produced by a model, compared with \code{==}, and shown to a reviewer in a diff of one line.

\section{Evaluation}
\label{sec:eval}

\subsection{Benchmark suite}

The Swarms repository already has a framework benchmark, \code{tests/benchmark.py}, which measures a flat fan-out. The suite introduced here extends it to workflows with structure.

\paragraph{Workflow shapes.}
Each shape is generated for $N$ agents, with $N \in \{8, 32, 128, 512\}$.
\begin{itemize}
  \item \textbf{Chain}: $N$ steps of one agent. Depth $N$.
  \item \textbf{Fan-out}: one step of $N$ agents. Depth 1.
  \item \textbf{Diamond}: one agent, then $N-2$ agents in parallel, then one agent. Depth 3.
  \item \textbf{Layered}: steps of eight agents, each step reading the one before. Depth $N/8$.
\end{itemize}

\paragraph{Frameworks.}
Every shape is built through the workflow API of each framework: \AR{} (Swarms 17, commit \code{aabfa8c}), \code{StateGraph} in LangGraph 0.5.4, the expression language of LangChain Core 0.3.63, AutoGen AgentChat 0.7.5 \code{GraphFlow}, Agno 3.2.0 \code{Workflow} and CrewAI 1.15.40 \code{Crew}. LangGraph appears twice, because its nodes can be plain functions or agents and the two cost very different amounts: \emph{LangGraph (functions)} uses a function per node that calls the model and appends to a list, the lightest graph LangGraph can run, and \emph{LangGraph (agents)} uses a prebuilt agent per node over a shared message state, which is the closer match to what \AR{} runs. A sequential CrewAI crew cannot end in more than one asynchronous task, so it cannot express the fan-out or layered shapes; those cells are empty.

\paragraph{Stubbed model.}
Every agent in every framework calls the same stub, which waits 10\,ms and returns a fixed string, through the framework's own model interface, synchronous or asynchronous as the framework prefers. No network is involved, so the differences measured are the frameworks' own work.

\paragraph{Metrics.}
Each cell (framework, shape, size) runs in a fresh interpreter after a small warm-up workflow.
\begin{itemize}
  \item \textbf{Orchestration overhead}: wall-clock time of a run minus the model time of that run. The stub records the start and duration of every call; the model time of a step is the duration of its fastest call, and the model time of a run is the sum over its steps. What is left is time the framework spent doing something other than waiting for a model. We report the median of three runs.
  \item \textbf{Peak memory}: the \code{tracemalloc} peak while building the agents and the workflow and running it once.
  \item \textbf{Construction time}: building the agents and the workflow.
  \item \textbf{Re-specification time}: changing the topology of an existing set of agents to a different shape and back, the median of four changes. For \AR{} this is \code{set\_custom\_flow}; for the others it is rebuilding the workflow object around the same agents, and for LangGraph recompiling it.
  \item \textbf{Peak threads} and the \textbf{number of model calls}, the latter as a check that every framework ran exactly $N$ calls, which all did.
\end{itemize}

\noindent All measurements were taken on one machine: Apple M3 Pro, 12 cores, 18\,GB, macOS 15.7, Python 3.12.3.

\paragraph{Wide workflows scale well.}
In the fan-out and diamond shapes \AR{} adds 37\,ms and 42\,ms at 512 agents, under a tenth of a millisecond per agent. That is 2.5 times less than LangGraph with function nodes (92\,ms and 105\,ms), about 9 times less than LangGraph with agent nodes (355\,ms and 372\,ms), 3 times less than LangChain, and more than two orders of magnitude less than AutoGen \code{GraphFlow}, whose overhead grows faster than linearly and reaches six seconds. Only Agno is in the same range, slightly lower on the diamond and slightly higher on the fan-out. At every size, \AR{} is within 8\,ms of the lowest overhead on both shapes.

\paragraph{Against graph frameworks whose nodes are agents, \AR{} is lower everywhere.}
\AR{} has less overhead than LangGraph with agent nodes, AutoGen \code{GraphFlow} and CrewAI in every one of the cells those frameworks can run, across all four shapes and all four sizes. The margin over LangGraph with agent nodes ranges from 1.6 times (layered, 512 agents) to 9.6 times (fan-out, 512 agents).

\paragraph{Deep workflows expose the cost of the shared conversation.}
The chain and layered shapes tell a different story at scale. Up to 32 agents \AR{} is the lowest or within 6\,ms of the lowest in every shape. At 128 agents and beyond its overhead in deep workflows grows faster than linearly: 887\,ms for a 512-agent chain and 991\,ms for 512 agents in 64 layers, against 186\,ms and 192\,ms for LangGraph with function nodes and 558\,ms and 100\,ms for Agno. The cause is the execution model of Section~\ref{sec:execution}. Before each agent runs, the whole conversation so far is rendered into messages for it, so step $k$ does work proportional to $k$ and a run does work proportional to the square of its depth. A LangGraph function node that appends one item to a list does constant work per step. The same effect appears in the frameworks that also pass history between agents: LangGraph with agent nodes and AutoGen are both slower than \AR{} on the 512-agent chain, at 2.2 and 6.4 seconds.

We consider this an honest trade and not a defect to be hidden. With a real model the same design makes the input of step $k$ grow with $k$, and the token bill, not the 1.7\,ms of orchestration per agent, is what a user of a 512-step chain would notice. Chains of that length are not what the language is for.

\paragraph{Memory follows the same split.}
For the wide shapes \AR{} has the lowest peak memory of any framework measured, 5.8\,MB for the fan-out and 5.9\,MB for the diamond. \paragraph{Construction is cheap and linear.}
Building 512 agents and their workflow takes about 8\,ms with \AR{}, which is 16 microseconds per agent. AutoGen and Agno are in the same range. LangGraph takes 31 to 49\,ms with function nodes and 167 to 246\,ms with agent nodes, since each prebuilt agent is itself a compiled graph.

\paragraph{Parallel steps cost threads.}

Threads are the reason \AR{} is not further ahead on wide shapes, and removing them is the first item of future work.

\section{Discussion and Limitations}
\label{sec:limits}

\paragraph{What the string buys.}
The flow string turns topology from code into data. That has consequences beyond brevity. A topology can be validated before any model is called, printed as a plan, stored next to prompts in configuration, swapped at run time without rebuilding agents, and written by a language model, since a one-line string in a two-operator grammar is an easy target for generation and an easy one to check. None of this is impossible with a graph API, but each step needs code there and needs none here.

\paragraph{What it gives up.}
The language is deliberately small, and the things it omits are real.
\begin{itemize}
  \item \textbf{No conditional edges and no cycles.} A flow always runs every step. Routing on a model's output, retrying until a critic approves, and other data-dependent control flow belong to LangGraph, to AutoGen's conditional edges, or to Swarms structures built for them. \code{max\_loops} repeats the whole flow a fixed number of times and is not a loop with an exit condition.
  \item \textbf{Series-parallel only.} Consecutive steps are fully connected. A dependency structure in which one agent of a step needs only some of the previous step's answers can be over-approximated but not stated exactly. \code{GraphWorkflow} in Swarms and the graph APIs of other frameworks cover general directed acyclic graphs.
  \item \textbf{One shared conversation.} Every member reads everything written before it. This removes plumbing code, but the context an agent receives grows with its position in the flow, so the total number of input tokens in a chain of $N$ agents grows as $N^2$. With real models this cost, not orchestration overhead, is what limits long chains. There is no per-edge state, typed channel or reducer of the kind LangGraph provides.
  \item \textbf{Names are the interface.} Agents are referenced by name, so names must be unique within a workflow and cannot contain a comma or the arrow. A misspelt name is caught at validation time, not by a type checker.
  \item \textbf{Threads for parallel steps.} A parallel step of $w$ agents holds $w$ threads for its duration. This is fine at the widths typical of real workflows and wasteful at hundreds of agents; Section~\ref{sec:eval} shows the cost.
  \item \textbf{No checkpointing.} A run is not resumable from the middle. The conversation can be saved after a run, but the workflow has no durable execution state.
\end{itemize}

\paragraph{Threats to validity.}
The benchmark isolates orchestration cost by stubbing the model, so it says nothing about answer quality, token cost or behaviour under rate limits, and with real models every overhead reported here is small next to a single model call. All numbers come from one machine and one version of each framework. We wrote the adapters for the other frameworks ourselves, from their public documentation, and a maintainer of any of them might write a faster one; the adapters are short and public so that they can be corrected. The comparison of specification size counts calls, which is a proxy for effort and not a user study.

\paragraph{Future work.}
Three directions follow directly from the measurements. The first is to run parallel steps on one event loop, as \code{ConcurrentWorkflow} in Swarms now does, which would remove the thread per agent. The second is to give members a bounded view of the conversation, for example only the previous step, to break the quadratic growth of context in long chains. The third is a small extension of the grammar, such as parentheses for inline nesting, so that a series-parallel workflow of any depth is still a single string.

\section{Conclusion}

\AR{} reduces the specification of a multi-agent workflow to a string with two operators. The string is short, it is validated before anything runs, it can be inspected and replaced on a live workflow, and, with nesting, it covers every series-parallel arrangement of agents. The benchmark suite released with this paper shows that the simplicity is not paid for in speed where the language is meant to be used: for workflows that are wide and a few steps deep, \AR{} has among the lowest orchestration overhead and the lowest memory of the frameworks we measured, and it is cheaper than every graph framework whose nodes are full agents at every size. The same suite shows where the design stops scaling, in chains of hundreds of agents that all read one shared conversation, and that result points at the next improvements. For the workflows that most multi-agent systems consist of, a line of text is enough.

\paragraph{Reproducibility.}
The benchmark suite is \code{tests/benchmark\_agent\_rearrange.py} in the Swarms repository. It needs no API key. Running \code{python tests/benchmark\_agent\_rearrange.py -{}-out results.json} regenerates every measurement behind Figures~\ref{fig:overhead} and~\ref{fig:rearrange} and Tables~\ref{tab:overhead}, \ref{tab:resources} and~\ref{tab:rearrange}; a framework that is not installed is reported as an error for its cells and the rest still run.
